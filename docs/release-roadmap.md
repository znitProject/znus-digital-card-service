# 검증 → 회사 Google 계정 전환 → Cafe24 배포 체크리스트

작성일: 2026-09-10

## 1. 확정한 방향

- 먼저 Google 테스트 배포에서 실제 화면과 설문 연동을 확인한다. 사용자가 검증 결과를 확인한 다음 Cafe24 운영 배포를 진행한다.
- 최종 공개 명함은 Cafe24와 회사가 관리하는 도메인에서 제공한다.
- 회사 Google 계정에 Drive·Sheet·Form·Apps Script를 새로 구성한다. 개인 테스트 데이터는 이전할 필요 없고, 동일한 기능을 재현하면 된다.
- 개인 테스트 URL·QR·NFC는 운영용으로 배포하지 않는다. 정식 QR·NFC는 최종 도메인을 확정한 다음 발급한다.
- 이미 실제 사용자에게 발급한 주소가 있다면 별도의 이전 계획으로 유지한다. 데이터 초기화 또는 계정 전환을 이유로 기존 주소를 임의 변경하지 않는다.
- 삭제된 공개 토큰은 재사용하지 않는다. 비활성화는 비공개 전환과 설문 수정 차단을 함께 수행하고, 재활성화만으로 공개하지 않는다.

## 2. 현재 상태와 한계

| 항목 | 확인된 상태 | 남은 일 |
| --- | --- | --- |
| 개인 계정 Form 자동화 | 개인 테스트 제출로 명함 생성·미디어 처리를 확인한 이력 있음 | 저장소 최신 코드와 실제 프로젝트 차이 정리, 재제출 회귀 검증 |
| 공개 화면 | 원본 디자인 기반 로컬 구현, Edge 데모 확인 | Google 배포에서 실제 데이터·권한·미디어 확인 |
| PNG·QR | 로컬 QR 표시, 626×1110 PNG 다운로드 확인 | Google iframe과 실제 회사 로고, 모바일에서 검증 |
| 관리자 화면 | 검색·수정·상태 변경·미리보기 코드 구현 | 운영 Sheet 바인드 연결 및 실제 권한 검증 |

| 완전 삭제 | 토큰 재사용 금지 기반만 구현 | 응답·시트 행·미디어·QR 영구 삭제와 실패 재시도 구현 |
| Cafe24 | 최종 운영 대상으로 결정 | 상품·도메인 확인부터 데이터 연결·배포까지 필요 |

로컬 자동 테스트 통과는 실제 Google OAuth, Drive 파일 접근, Google 배포, Cafe24 동작을 보장하지 않는다. 아직 배포만 남은 상태가 아니다.

## 3. 선행 작업: Google 배포로 시각적·기능적 검증

Google Apps Script 웹 앱으로 실제 명함 화면을 확인할 수 있다. 테스트 주소는 `https://script.google.com/macros/s/<deployment-id>/exec?card=<token>` 형태다. 원하는 도메인은 여기에서 직접 설정하지 않고, 최종 Cafe24 환경에서 연결한다.

### 3.1 테스트 환경 완성

- [ ] 기존 개인 공개 프로젝트를 재사용한다. 프로젝트명은 `ZNUS 공개 명함 (개인 테스트)`이며 위치는 [4단계 기록](stage-4.md)에 있다.
- [ ] 공개 프로젝트의 Code.gs·Card.html·appsscript.json을 저장소와 대조한다. 화면과 코드를 거대한 한 줄 문자열로 합치지 않는다.
- [ ] manifest가 Sheets·Drive 읽기 전용 권한인지 확인한다. 관리자 쓰기·삭제 RPC는 공개 프로젝트에 포함하지 않는다.
- [ ] 개인 계정의 읽기 권한·익명 공개 설정은 사용자가 이미 승인했다. 실제 Google 인증·설정 저장 완료 여부를 확인한다. 별도 2차 인증이 뜨면 계정 소유자가 수행한다.
- [ ] `ZNUS_SPREADSHEET_ID`와 실제 데이터 Sheet를 확인한다.
- [ ] 네 기본 영상과 배경 이미지·로고의 HTTPS 제공 경로를 마련하고 `ZNUS_ASSET_BASE_URL`을 연결한다. 이전에 확인한 jsDelivr 경로는 404였으므로 정상 경로로 간주하지 않는다.
- [ ] 공개 웹 앱을 배포자 권한으로 실행하고 익명 접근을 허용하는 테스트 배포를 생성한다. 배포 ID·버전·URL을 기록한다.
- [ ] 개인 테스트 명함의 빈 `publicUrl`만 테스트 주소로 채운다. 회사 운영 주소와 섞지 않는다.
- [ ] 로그인하지 않은 브라우저에서도 공개 명함만 보이는지 확인한다.

### 3.2 화면 확인 체크리스트

- [ ] 프로필 사진, 이름 국문·영문이 실제 Form 응답과 일치한다.
- [ ] 부서, 직함, 직무 5개가 정확하고 한국어·영문 전환이 동작한다.
- [ ] 연락처, 회사 로고·슬로건·주소, 홈페이지·지도 링크가 일치한다.
- [ ] 인트로·카드 이동·스크롤과 긴 이름·긴 직함·긴 이메일 레이아웃을 확인한다.
- [ ] DEFAULT·IMAGE·VIDEO를 각각 확인한다. 업로드 영상은 무음·반복·인라인 재생하며 재생 실패 시 화면 정보는 읽을 수 있어야 한다.
- [ ] 실제 기기의 Android Chrome·iPhone Safari·PC Edge에서 확인한다. PC 화면 크기 변경만으로 모바일 검증을 대체하지 않는다.
- [ ] QR을 실제 카메라로 스캔하면 해당 명함으로 이동한다. 공유 주소는 Google 내부 iframe 주소가 아니라 저장된 공개 주소다.
- [ ] PNG가 실제 로고·텍스트를 포함한 626×1110 파일로 저장되고 프로필·영상·버튼은 포함하지 않는다.

### 3.3 실제 연동 및 관리자 검증

- [ ] 신규 설문 제출 → 처리 중 → 완료 → 명함 공개까지 확인한다.
- [ ] 동일 계정 재제출 시 UUID·공개 토큰·주소는 유지되고 내용만 변경된다.
- [ ] 신규 배경 미첨부는 기본 배경, 수정 시 미첨부는 기존 배경 유지, 관리자 기본값 복원은 업로드 배경 해제를 확인한다.
- [ ] JPG·PNG·WEBP 및 3~5초 MP4를 확인하고, 5초 초과·18MiB 초과·해상도 초과·손상 파일·잘못된 형식은 거부되는지 확인한다.
- [ ] 비공개 상태에서는 방문자가 볼 수 없지만 설문 수정은 가능하다.
- [ ] 비활성 상태에서는 공개 조회와 설문 수정 반영이 차단되고, 재활성화 후에는 비공개가 유지된다.
- [ ] 관리자 검색·통계·정보 수정·파일 교체·미리보기를 실제 Sheet에서 확인한다.
- [ ] 동시 제출·동시 편집에서 중복 카드나 오래된 데이터 덮어쓰기가 발생하지 않는다.
- [ ] 파일 처리 오류 시 상태·원인이 남고, 이전 정상 명함과 자산이 불필요하게 손실되지 않는지 점검한다.
- [ ] 시나리오별 결과·스크린샷·오류·수정 커밋을 기록하고 사용자에게 검토받는다.

## 4. 후속 작업 A: 회사 Google 계정으로 기능 재구성

### A1. 회사 환경과 소유자 확정

- [ ] 회사 운영 계정과 관리자를 정하고, 조직의 Apps Script·OAuth·외부 공개·파일 업로드 정책을 확인한다.
- [ ] 계정 정책상 필요한 승인·2차 인증을 준비한다. 개인 계정에서 승인됐다고 회사 계정에서도 동일하게 된다고 가정하지 않는다.
- [ ] 회사 계정이 소유할 My Drive 또는 Shared Drive 중 사용할 저장 위치를 정한다. Shared Drive 선택 시 Form 파일 업로드와 스크립트 동작의 지원 여부를 실제로 확인한다.
- [ ] 개인 테스트 데이터를 복사하지 않는 새 환경임을 확인한다. 개인 테스트 데이터 삭제는 별도 작업으로 취급한다.

### A2. Drive·Sheet 생성

- [ ] 회사 계정에 전용 루트, 관리자, Form 업로드, 카드 자산, 생성물·QR 폴더를 구성한다.
- [ ] 폴더는 기본적으로 제한된 접근을 사용하고 운영자만 편집할 수 있게 한다.
- [ ] 새 Sheet에 Cards·CompanySettings·DeletedTokens와 Form 응답 저장 시트를 구성한다.
- [ ] 회사 공통정보·로고를 실제 운영값으로 입력한다. 데모 이름·주소·전화가 남지 않게 한다.
- [ ] 서비스에서 실제 발급·삭제된 운영 토큰이 기존에 있다면 재사용 금지를 유지할 방법을 정한다. 직원 개인정보 이관과 토큰 재사용 방지는 구분한다.

### A3. 한국어 Form 재구성

- [ ] 국문·영문 이름, 부서·직함, 직무 5개씩, 공개 전화·이메일 필드를 생성한다.
- [ ] Google 계정 이메일 수집을 설정하고 같은 계정의 재제출을 허용한다. 공개 이메일과 제출 계정 이메일은 구분한다.
- [ ] 프로필 이미지 업로드를 필수로 설정하고 이미지 형식 제한을 안내한다.
- [ ] 직무·연락처·회사·링크 배경 업로드를 선택 항목으로 만들고 모든 업로드 질문을 최하단에 둔다. 배경 모드 선택 질문은 만들지 않는다.
- [ ] 신규 미첨부/수정 미첨부 동작, MP4 최대 5초·18MiB·2560×1440 제한을 사용자가 이해하기 쉽게 안내한다. Form 설정으로 강제하지 못하는 조건은 서버에서 검증한다.
- [ ] 새 Form을 회사 Sheet에 연결한다. 이미 파일 업로드 질문이 있는 Form에 질문 재생성 함수를 실행하지 않는다.

### A4. Apps Script·관리자 구성

- [ ] 회사 Sheet에 바인드된 관리자 프로젝트를 만들고 `apps-script/admin-bound` 최신 코드를 반영한다.
- [ ] `ZNUS_SPREADSHEET_ID`, `ZNUS_FORM_ID`, `ZNUS_FOLDER_*`를 회사 환경 값으로 설정한다. 개인 계정 ID가 남지 않게 한다.
- [ ] `connectExistingForm(formId)`로 응답 저장 위치·이메일 수집·기존 연결을 검증한다.
- [ ] 회사 운영 계정으로 필요한 Google 권한을 승인하고 설치형 Form 제출 트리거를 한 개 등록한다.
- [ ] `inspectFormConnection()`과 각 프로젝트의 트리거 화면을 확인한다. 다른 계정·프로젝트의 중복 트리거는 이 함수에서 모두 보이지 않는다.
- [ ] 관리자 화면을 실제 운영자 권한으로 열고 비운영자의 접근이 차단되는지 확인한다. 관리자 프로젝트는 익명 공개 배포하지 않는다.
- [ ] Cafe24에서 사용할 공개 데이터 제공 프로젝트/연결을 회사 환경으로 구성한다. 선택한 연결 방식에 맞춰 필요한 권한만 부여한다.
- [ ] 배경 자산 경로와 최종 공개 기본 URL을 설정한다. 운영 명함을 생성하기 전에 도메인을 확정한다.

### A5. 전환 검증 및 운영 인계

- [ ] 회사 계정에서 3절의 제출·수정·미디어·상태 변경 검증을 다시 수행한다.
- [ ] 계정 이메일 변경 시 응답 이력·자산 소유권·완전 삭제 대상 추적이 유지되도록 구현하고 검증한다.
- [ ] 파일 선택 UI, 관리자 QR 다운로드, 완전 삭제·실패 재시도를 마무리한다.
- [ ] 완전 삭제는 대상 확인 후 수행하며 Form의 해당 직원 응답들, 응답 시트 행, 카드 자산·교체 원본·QR을 정리한다. 타인의 파일이나 회사 공통 자산은 삭제하지 않는다.
- [ ] 삭제 실패 시 비공개·수정 차단을 유지하고 재시도할 수 있게 한다. 성공 후 개인정보가 없는 토큰만 DeletedTokens에 남는지 확인한다.
- [ ] 관리자에게 오류 확인·재처리·상태 변경·삭제·설정 관리 방법을 인계한다.
- [ ] 회사 환경 검증 후 개인 테스트 자동화를 중지할 시점과 테스트 데이터 정리 여부를 결정한다. 검증 전에 개인 환경을 삭제하지 않는다.

## 5. 후속 작업 B: Cafe24 최종 배포

### B1. 배포 환경 확정

- [ ] Cafe24 호스팅 상품, 사용 가능한 런타임(PHP/Node 등), 외부 HTTPS 요청, 업로드 제한, 저장공간·트래픽 한도를 확인한다.
- [ ] 관리할 도메인 또는 `card.<회사 도메인>` 하위 도메인, DNS 변경 권한, HTTPS 인증서 설정을 확인한다.
- [ ] 배포 디렉터리, 파일 전송 방식, 운영·검증 환경 구분, 접근 권한을 정한다. 인증정보를 저장소나 문서에 기록하지 않는다.

### B2. Cafe24 데이터 연결 구현

- [ ] 현재 화면의 `google.script.run` 호출을 Cafe24에서 동작하는 조회 어댑터로 교체한다. 파일만 업로드해서는 현재 코드가 그대로 동작하지 않는다.
- [ ] 호스팅 지원 환경에 맞춰 서버 중계 또는 사전 생성 공개 데이터 방식을 확정한다. Google의 CORS·인증·리다이렉트와 실제 호스팅 기능을 검증한 다음 선택한다.
- [ ] 공개 DTO만 전달한다. 내부 UUID·Google 계정 이메일·오류 메시지·관리자 기능·비밀 키를 브라우저 응답에 포함하지 않는다.
- [ ] 토큰 형식과 공개·활성 상태를 서버에서 검사하고, 비공개·삭제된 토큰·존재하지 않는 토큰의 응답을 정의한다.
- [ ] 캐시를 사용하는 경우 수정·비공개·비활성·삭제 시 즉시 반영되도록 무효화 경로를 구현한다.
- [ ] `/명함토큰` 경로 라우팅, 직접 주소 접속, 새로고침, 잘못된 주소 처리를 구현한다.
- [ ] Google 연결 오류·시간 초과 시 안내 및 재시도 동작을 구현한다. 필요하면 오류 로그와 요청 제한을 설정한다.

### B3. 이미지·영상 경로와 화면 이식

- [ ] 원본 네 배경 영상·배경 이미지·SVG 로고·폰트 제공 방식을 정하고 정상 MIME 형식·HTTPS 접근을 확인한다.
- [ ] 업로드 미디어를 Drive에서 제공할지, Cafe24로 동기화할지 확정하고 구현한다. Drive 썸네일/다운로드 주소만으로 안정적인 영상 제공이 된다고 가정하지 않는다.
- [ ] 동기화한다면 신규·교체·기본값 복원·완전 삭제까지 양쪽 자산의 수명주기를 맞춘다.
- [ ] 비공개·삭제 처리 시 미디어 직접 URL이 계속 공개되는 범위를 확인하고 정책에 맞게 접근권한·캐시도 정리한다.
- [ ] 영상의 재생 지연·모바일 메모리 사용·트래픽을 확인하고 필요 시 포스터·압축·지연 로딩을 개선한다.
- [ ] 원본 디자인, 한영 전환, 연락처·지도·공유, QR·PNG 저장을 Cafe24 환경에서도 유지한다. PNG 로고의 CORS 문제도 확인한다.

### B4. 검증 배포와 정식 전환

- [ ] 동일한 회사 Google 환경을 사용하는 Cafe24 검증 주소에서 전체 흐름을 재검증한다.
- [ ] PC·모바일, 로그인하지 않은 방문자, 운영자·비운영자의 접근을 확인한다.
- [ ] 사용자에게 실제 화면·테스트 결과·남은 제한을 보여주고 정식 배포 시점을 확인한다.
- [ ] 확정된 빌드·커밋, 환경 설정, 서버 파일과 DNS 변경 전 상태를 기록해 롤백을 준비한다.
- [ ] 최종 도메인·HTTPS·라우팅·데이터 연결을 적용한다. 불필요한 관리자 파일·배포 소스·인증정보는 공개 디렉터리에 올리지 않는다.
- [ ] 최종 `publicUrl`을 기준으로 QR·NFC를 생성하고 실제 스캔·태그 접속을 확인한다.
- [ ] 기존에 실제 배포한 주소가 있다면 리다이렉트 또는 호환 라우트를 유지하고 검증한다.
- [ ] 신규 제출·수정·비활성·삭제를 운영 환경에서 최종 점검한다. 테스트용 삭제는 지정한 폐기 가능한 명함으로만 수행한다.
- [ ] 장애 시 이전 배포로 복구할 절차와 연락 담당자를 문서화한다.

## 6. 실행 순서와 완료 기준

1. **Google 개인 테스트 배포**: 실제 명함 URL에서 화면·영상·PNG·설문 수정 흐름을 확인하고 사용자 피드백을 반영한다.
2. **미완료 기능 구현**: 관리자 실연결, 완전 삭제, 파일 선택, QR 다운로드 및 발견된 오류를 처리한다. Cafe24 연결 개발은 상품 확인 후 병행할 수 있다.
3. **회사 Google 환경 재구성**: 테스트 데이터 이전 없이 동일 기능을 새 계정에서 재현한다.
4. **Cafe24 검증 환경**: 회사 Google 데이터와 연결하여 실제 최종 구조를 검증한다.
5. **정식 배포와 인계**: 사용자 확인 후 도메인·QR·NFC를 적용하고 운영 방법을 전달한다.

각 단계는 코드 작성만으로 완료 표시하지 않는다. 실제 환경의 테스트 결과, 사용한 커밋·배포 버전, URL, 담당자와 남은 이슈를 기록한 뒤 체크한다.
