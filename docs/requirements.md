# ZNUS 디지털 명함 서비스 요구사항

## 1. 목표와 원칙

Google Form·Sheets·Drive·Apps Script·Cafe24에 의존하지 않고, DB부터 입력 페이지와 공개 배포까지 하나의 자체 서비스로 운영한다.

직원 수는 고정하지 않는다. 직원 추가·비활성화·재등록은 DB 레코드 상태로 처리하며, 입력 페이지와 공개 카드 템플릿은 직원 수와 무관하게 하나만 운영한다.

## 2. 기술 설계

- 백엔드 프레임워크: Fastify
- 언어: TypeScript
- 데이터베이스: PostgreSQL
- DB 접근: Prisma Client 및 Prisma migration
- 입력 검증: Zod
- 직원 인증: 회사 이메일 OTP와 HttpOnly 세션 쿠키
- 파일 업로드: Fastify multipart 플러그인
- 화면: 기존 `cardDesign` HTML/CSS를 재사용한 서버 제공 화면과 vanilla JS
- 실행: 앱은 Docker Compose로 배포하며, 개발 단계에서는 PostgreSQL만 별도 Docker Compose로 실행할 수 있다.
- HTTPS: Caddy 또는 사내 Reverse Proxy

현재 저장소의 `server/`는 먼저 동작 검증을 끝낸 Node.js 서버 세로 슬라이스이며, API 계약과 Prisma migration을 기준으로 유지한다. Fastify·TypeScript 전환은 운영 배포 전에 별도 리팩터링 단계로 진행한다.

## 3. URL 구조

- `/input`: 모든 직원이 사용하는 공용 입력·수정 페이지
- `/{publicToken}`: 공개 명함 페이지 (기존 `/c/{publicToken}` 링크는 호환)
- `/admin`: 운영자용 관리 화면
 - `/healthz`: 서비스와 DB 상태 확인

기존 대시보드의 시각적 디자인과 정보 구조는 유지한다. 데이터 조회·미리보기·상태 표시·관리 동작의 구현만 PostgreSQL API 기준으로 교체한다.

공개 명함 토큰과 직원 수정 권한은 반드시 분리한다. 공개 URL을 알고 있다고 해서 수정할 수 없어야 한다.

## 4. 직원 접근 방식

1. 직원이 `/input`에서 회사 이메일을 입력한다.
2. 서버가 허용 도메인을 확인하고 6자리 OTP를 발송한다.
3. 직원이 OTP를 입력하면 입력 세션을 발급한다.
4. 기존 직원이면 자신의 레코드를 수정하고, 신규 이메일이면 직원 레코드를 생성한다.
5. 세션 만료 후 다시 OTP를 확인한다.

별도 회원가입·비밀번호·Google 계정 로그인은 사용하지 않는다. OTP 원문은 저장하지 않고 해시만 저장하며, 만료·시도 횟수 제한·재발급을 적용한다.

## 5. 직원 데이터

- 회사 이메일, 선택적 사번
- 이름 국문·영문
- 부서
- 직책 국문·영문
- 공개 휴대전화
- 공개 이메일
- 주요 업무 국문 5개·영문 5개
- 공개 토큰
- 상태: `ACTIVE`, `INACTIVE`, `DELETED`
- 공개 여부와 생성·수정 시각

비활성화 또는 삭제된 직원은 OTP로 입력 세션을 만들 수 없고 공개 명함도 표시하지 않는다.

## 6. 미디어와 디자인

이미지·영상은 PostgreSQL에 직접 저장하지 않는다. DB에는 파일 ID, 저장 키, MIME 타입, 크기, 카드 슬롯만 저장한다.

지원 슬롯은 프로필, 직무, 연락처, 회사, 링크 배경과 회사 로고다. 기존 `cardDesign/명함_디자인`의 콘텐츠와 한영 전환, QR, 공유, 간략 명함 PNG 기능을 새 공개 카드 화면에 연결한다.

지원 형식은 JPG/JPEG·PNG·WEBP 이미지와 MP4 영상이다. 영상은 음소거·반복·인라인 재생하며 파일 유형과 최대 30MB 크기를 서버에서 검증한다.

## 7. 데이터베이스와 저장소

운영 PostgreSQL은 `100.102.230.73` PC의 Docker 컨테이너에서 실행한다. 현재 개발 단계에서는 앱을 개발 PC에서 실행하고 Tailscale 사설망을 통해 `100.102.230.73:5432`에 접속한다. PostgreSQL은 `100.102.230.73` 인터페이스에만 바인딩하고, Windows 방화벽에서도 Tailscale 대역만 허용한다. 이후 앱을 원격 PC로 옮기면 앱과 DB를 같은 Docker 네트워크에 둘 수 있다.

초기 테이블:

- `company_settings`
- `employees`
- `media_assets`
- `otp_challenges`
- `input_sessions`
- `audit_logs`
- `deleted_tokens`

프로필과 영상 파일은 파일 저장소에 두고, DB에는 메타데이터와 저장 키만 보관한다. DB 볼륨과 미디어 저장소는 별도 백업한다.

## 8. 관리자 기능

관리자는 직원 목록·검색, 카드 미리보기, 공개·비공개, 활성·비활성, 삭제·복구, 회사 설정, 수정 링크 재발급을 할 수 있다.

관리자 화면은 직원용 공용 입력 세션과 분리된 인증을 적용한다. 관리자 기능을 무인증으로 공개하지 않는다.

## 9. 공개 카드와 오류 처리

정상 저장된 직원만 공개 명함을 제공한다. 신규 카드의 공개 토큰은 한 번 발급하고 수정해도 유지한다. 삭제된 토큰은 `deleted_tokens`에 남겨 재사용하지 않는다.

미디어 처리나 저장에 실패하면 기존 정상 공개 카드는 유지하고, 실패 상태와 오류 메시지를 관리자 화면 및 감사 로그에 남긴다.

직원이 비활성화되거나 삭제되면 기존 URL은 ‘이용할 수 없는 명함입니다’ 화면을 표시한다.

## 10. 배포와 운영

- Node.js 서비스와 PostgreSQL은 Docker Compose로 실행한다.
- `100.102.230.73`은 사설망/Tailscale 주소로 사용한다.
- 공개 서비스는 도메인과 HTTPS를 사용한다.
- 환경변수와 SMTP 비밀번호는 저장소에 커밋하지 않는다.
- `healthz`, 컨테이너 로그, DB 백업을 운영 점검 기준으로 사용한다.
- Google 연동 파일·Apps Script·Cafe24 배포 스크립트는 운영 코드에 포함하지 않는다.
